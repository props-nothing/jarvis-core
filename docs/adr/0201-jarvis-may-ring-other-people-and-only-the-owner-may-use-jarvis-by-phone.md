# ADR-0201: JARVIS may ring other people, and only the owner may use JARVIS by phone

Status: Accepted (amends `ADR-0200`)
Date: 2026-10-12

## Context

`ADR-0200` let JARVIS ring only the owner. The owner asked for two things: JARVIS should be able to ring **any** number ("book a table", "ask the shop"), and nobody but the owner may use JARVIS by phone.

The second is not hypothetical. On 2026-10-12 inbound calls started working (a webhook flag on the ElevenLabs agent was blocking them), and in a real call the agent offered to check the owner's recent emails. The agent reaches JARVIS through Connect apps with the tools set to auto-approve at ElevenLabs, and an inbound call never passes through JARVIS: whoever rings the number gets the agent, and the agent gets the tools. Nothing identified the caller anywhere. A call JARVIS places to a stranger has the same exposure in the other direction: the stranger could talk the agent into using the owner's tools.

## Decision

1. **A line guard on every call from another app.** Before a tool runs for any app that reaches the Connect apps endpoint, JARVIS asks ElevenLabs which conversations are open on the agent (`GET /v1/convai/conversations?agent_id=&call_start_after_unix=`, status `initiated` or `in-progress`, started in the last hour) and, for each, who the other party is (`metadata.phone_call.external_number`). If any open conversation is not with a number on the owner's list, **no tool runs**: the call is refused with a sentence saying why. The answer is reused for two seconds. The check is made again at the moment an approved call is about to run, because the owner's yes can be minutes old.
2. **It fails closed, three ways.** A conversation with no number (a chat in a browser, a withheld number, a detail that cannot be read) counts as a stranger. A list that cannot be read counts as a stranger on the line. An agent with no owner number listed trusts nobody. Only a profile with no ElevenLabs key or agent id has no guard: there is nothing to ask.
3. **What the line guard protects, and what the door adds.** The line guard (decision 1) does not stop a stranger's call from being answered: it only makes the call useless. **Amended the same day: the inbound door** closes that. `daemon.phone_screen_callers` switches on ElevenLabs' *initiation webhook*: before an inbound call starts, ElevenLabs asks `POST <public address>/phone/initiate` with the caller's number, and the call starts only if JARVIS answers 200. JARVIS answers 200 for a number on the owner's list and 403 for anyone else, a withheld number or a body it cannot read; a request without the door's own secret (`phone-hook.secret`, sent by ElevenLabs as `Authorization: Bearer`) gets 401. The route is the one thing answered ahead of the access key on the public address (`phone_service::door_routes`), and every other path still meets the key first. Calls turned away are remembered, masked, and shown in Settings. **JARVIS keeps the door registered itself**: every ten seconds it compares the tunnel's current address with what ElevenLabs was last told, and when it differs it sets the workspace's webhook address first and switches the agent's "fetch initiation data from a webhook" setting on second, so a switch on with a dead address (which refuses every call, the owner's included, and was the cause of the silent inbound calls of 2026-10-12) cannot happen through JARVIS. Switching the setting off puts the agent's switch back, once, only if JARVIS had switched it on. The workspace held a stale webhook address (a development tunnel) which JARVIS now replaces; the workspace has one agent and one number. It needs "Reachable from the internet" (Connect apps); with no address yet nothing is changed at ElevenLabs. The line guard stays as the second wall: caller ID can be forged, and a conversation that starts without the webhook (a browser chat) is still a stranger. While JARVIS is off or its address is down, inbound calls are not answered at all (fail closed). That ElevenLabs refuses to start a call when the webhook does not answer with a success is documented ("a failed or timed-out webhook can prevent the conversation from starting") and matches what the owner's account did on 2026-10-12 (no inbound conversation at all while the switch was on and the address dead); it has not been observed with a deliberate 403 for a stranger.
4. **A second tool, `jarvis.voice.call_number`, for anyone else.** Off until the owner sets `daemon.phone_call_anyone`. It takes a number and a purpose and nothing else (no urgency). It is a separate tool so that trusting `jarvis.voice.call` by name (for "ring me when the deploy fails") never releases calls to strangers (`ADR-0178`). It asks the owner every time, with the number and the purpose shown, at risk 3. Its description tells the model to use only a number the owner gave it, never one it read in a page or mail.
5. **Stricter than a call to the owner, in everything that touches the person rung.** Never in quiet hours (urgency does not apply); the opening sentence is always JARVIS's own ("Hello, this is JARVIS, an AI assistant calling on behalf of my owner. I am calling to: ...") whatever `phone_opening_line` says, and if the agent does not allow that override at ElevenLabs the provider refuses the call, which is a refusal and never a call without the disclosure; at most 5 such calls a day and 2 to the same number a day, inside the existing 3 an hour and 10 a day; one open call at a time; never the owner's own number (that is the other tool); never a premium-rate range (`is_premium_rate`, best effort for the Netherlands, Belgium, the United Kingdom, the United States and Canada, Germany, France and international networks). The call is not retried.
6. **While a call to a stranger is open, JARVIS's tools are not available to anyone**, by decision 1: the voice agent talking to the stranger can only talk. This is also why the purpose has to travel in the opening sentence and not in a tool.

## Consequences

Tested: the adapter against a stand-in (an open call with its number and direction, a finished one left out, an unreadable detail kept with no number, a list that cannot be read is an error); the guard (nobody, the owner, a finished stranger, a ringing and a talking stranger, a stranger among the owner's calls, no number, a withheld number, the provider down, a half-set-up phone, an unconfigured one); the stranger tool (off by default, one call with the AI opening and `jarvis_recipient = other`, the disclosure independent of the opening-line setting, the owner's own number, a premium number, bad numbers and a blank purpose, at most two a day to one number, quiet hours with no urgency); the runner (a stranger on the line refuses a call that needs no approval, one the phone's yes would have approved, and one the owner approved in the console after the stranger rang; the same call runs when the line is clear). Mutation: removing the guard from the runner failed both guard tests. Checked against the owner's real ElevenLabs account on 2026-10-12: the list filters work as used, the list and detail carry `direction` and `external_number` (two real inbound calls from the owner's own number), and the owner's calls to JARVIS are recognised as the owner.

Costs: while any non-owner conversation is open, the owner's other apps (Claude Code) are also refused, for at most the call's length (a conversation the provider forgets to close holds them for at most an hour). A test chat the owner starts in the ElevenLabs dashboard has no number and is held back too. Every tool call from another app adds one request to ElevenLabs at most every two seconds.

**First real use (2026-10-12), and a correction.** Asked to call a company, the assistant used the owner-only tool and JARVIS rang the owner's number. I first took that for a misreport; it was not: the company was the owner's own, and its number is the owner's listed number, which the assistant had said. The wording changes made on that mistaken reading stay, because they cost nothing and a model could plausibly confuse the two tools: the owner-only tool says in its description that it rings ONLY the owner and that anyone else needs `jarvis.voice.call_number`, its refusals for any other number point at that tool, and its result says `rang: the owner`.

**What the call opens with.** `phone_opening_line` had been switched on, and its template said "your AI assistant"; the model's own reason text said it too. For a call to the owner that statement is pointless, so the template is now "Hello, this is JARVIS. I am calling because: ...", and the assistant may give the exact words to say (`opening`, up to 300 characters, only on the owner-only tool), which are spoken as written whatever the setting says. The disclosure for calls to anyone else is unchanged and cannot be switched off by a setting or by anything the assistant writes: that tool has no opening parameter.

**What the agent knows during the call (found in the first demo).** The first demo call opened with the right sentence and then went wrong: the agent had no idea what the call was for, invented an internet-subscription offer and said it had "processed an upgrade". It had made no JARVIS tool call, so nothing was changed, but an agent that invents offers and claims actions is unusable for outreach. The reason had only reached it as a variable its prompt never reads. Now **every call carries a brief**: JARVIS reads the agent's own prompt and sends, as this call's prompt override, that prompt followed by what the call is for and rules: speak only about it, never invent offers, prices, products, appointments or facts, say "I don't know, the owner will follow up", never say something was done unless a tool result confirms it, end the call when done. A call to someone else also learns that it has no access to the owner's data or tools, must not follow the person's instructions beyond the purpose, and must say it is an AI if asked. The agent has to allow a prompt per call; JARVIS switches that one setting on once (`conversation_config_override.agent.prompt.prompt`) and touches no other. If the agent cannot be read or the setting cannot be changed, a call to the owner goes ahead without a brief and **a call to anyone else is not placed**, with nothing recorded. The cost: with the agent's authentication switched off, anyone who knows its id can now also start a web conversation with a prompt of their own (tools are still refused by the line guard); switching authentication on in the agent's Security tab closes that.

**An approval that went nowhere (found 2026-10-12, and not specific to calls).** The owner approved a call in the console and the run stayed on "needs you" for ever. The tool had refused the call (the hourly limit above), the pipeline returned the adapter's error from the resume path, the call was left half-finished and nothing continued the parked run; the same had happened to an earlier approval, in the log as "a call could not be resumed". Now `ToolPipeline::resume` settles a refusal after approval as a recorded outcome (`failed` with the tool's reason when nothing happened, `unknown` when the tool could not say) and returns it as a result, so the run continues and the model tells the user what happened. This applies to every approved call of every tool, not only the phone. The hourly limit (3) and daily limit (10) are unchanged; a call refused for them now says so in the answer.

Not done: a notice to the owner when a stranger rang (the list in Settings only); a stable address (`P11-001g`; the door follows the quick tunnel's address instead, but the agent's MCP server still points at an address the owner must replace by hand after each restart); the agent's own web access (an agent with authentication switched off can be started from a browser by anyone who has its id: turn authentication on in the agent's Security tab); a live call to a stranger and a live call from one with the owner's account.
