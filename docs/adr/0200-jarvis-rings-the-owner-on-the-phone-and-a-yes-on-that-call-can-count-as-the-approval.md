# ADR-0200: JARVIS rings the owner on the phone, and a yes on that call can count as the approval

Status: Accepted (first slice of `P8-007`; amends `ADR-0180`; amended by `ADR-0201`: other people can be rung, and a guard keeps everyone but the owner away from the tools)
Date: 2026-10-11

## Context

The owner connected an ElevenLabs agent to JARVIS's MCP endpoint (`ADR-0170`) and let it ring them: it worked. Two things were missing. JARVIS itself could not decide to call ("call me when the deploy fails"), and the approval was asked twice: the agent asked on the phone (tool approval set in ElevenLabs), and the same call then waited in the console (`ADR-0180`) for a click the owner could not give, because they were on the phone. Research: `docs/research/integrations/elevenlabs.md` (the phone calls section).

## Decision

1. **The provider talks; JARVIS decides and keeps the record.** An ElevenLabs agent with a phone number runs the call. JARVIS asks it to ring (`POST /v1/convai/twilio/outbound-call` or `.../sip-trunk/outbound-call`, by the number's provider) and reads how it went (`GET /v1/convai/conversations/{id}`) every ten seconds while a call is open. No webhook: it works with no public address. The agent's tools stay JARVIS's: it reaches them through Connect apps, so every call it makes passes the same policy.
2. **Two tools, `jarvis.voice.call` and `jarvis.voice.status`.** (The architecture sketch said `voice.call.start`; a tool id is `namespace.name` with a single final name, so the names are flat. There is no `end`: the provider documents no way to hang up.) A call is an external communication of risk 2: it **asks the owner every time** unless the owner trusted it by name (`ADR-0178`), which is how "call me if the deploy fails" works unattended. Status is read-only and returns the provider's summary and what was said **fenced as data**. The family is deferred like calendar and schedule (`ADR-0197`).
3. **Only a number the owner listed.** `daemon.phone_owner_numbers` (international format, at most five, stored in one canonical form) is the whole list. A model gives a reason and optionally one of those numbers; nothing else can be rung. The first listed number is the default.
4. **Rules that hold even when trusted**, in one function (`PhoneService::start_call`) used by the tool and the Settings button alike: quiet hours stop a call unless the model marks it urgent (`daemon.quiet_hours`, `ADR-0195`); at most 3 calls an hour and 10 a day, counting every call that was started; one open call at a time; a reason of 1 to 500 characters. A refusal comes before anything is recorded or sent.
5. **Recorded before it rings, never retried.** A row (`phone_calls`, migration 0024, schema 24) is written with the status `starting` before the provider is asked. A request that gets no usable answer is `Uncertain`: the record stays open (so the line stays busy and the count includes it), the tool result is "reached, outcome unknown", and the poller writes it off after two minutes. A finished call is never changed again, and a status never moves backwards. The record holds who (the number), why, urgency, status, duration, why it ended and the provider's summary. **Transcript and audio are not kept**; the status tool reads the transcript from the provider on request. Records older than 90 days are removed at start and "Delete call records" clears them.
6. **Not served to other apps.** The phone tools are not in the Connect apps surface (`servable_definitions`): the phone agent is itself such an app, and one that could place the next call could keep the owner's phone ringing.
7. **A yes on the phone can be the owner's answer, narrowly.** `daemon.phone_approves` (off by default). When a call from another app waits for the owner (`ADR-0180`), the runner first asks the phone service whether the owner is on a call JARVIS placed. It counts only if: the setting is on; a call JARVIS **placed to a number on the list** is `in-progress` (answered, not ringing) and under 30 minutes old; the tool's risk is 2 or less; the tool is not a phone tool; and the owner has not set that tool to "Always ask first" (tightening outranks). The receipt cites the call (`phone-<call id>`) and the approver `local-owner:phone`. Otherwise the question waits in the console exactly as before. A call someone else places to the provider's number never qualifies, because a caller's number is not proof of who is speaking (`docs/architecture/voice-and-telephony.md`).
8. **Settings, Phone** (no restart; each use reads the saved configuration): agent id, phone number id, numbers, the two flags, a "Call me now" button (the owner's own request, so no approval; every other rule still applies), "Check with ElevenLabs" (finds a wrong id or an unsupported number, shows the number ids, says if the number answers with another agent), and the recent calls. The key is the existing voice key. `jarvis config` reaches the same settings.
9. **Calls the owner makes to JARVIS** are the agent answering its imported number and using JARVIS's tools through Connect apps, as the owner already tried. JARVIS adds no new entry point for them in this slice (see "Not done").

## Consequences

Tested: the adapter against a stand-in (Twilio and SIP endpoints, override only on request, refusal and 422 reasons with the key removed, a non-answer is `Uncertain` and is sent once, bounded identifiers); storage (written before the call, never backwards, rate window, retention, bounds); the service (nothing rings unconfigured, only a listed number, quiet hours and urgent, one at a time, 3 an hour, a refusal frees the line, an uncertain request keeps it, the phone's yes only while answered and listed and enabled, masked numbers in Settings); the tools (declarations, schema takes no other field, deferral, fencing of what was said, error mapping to ambiguous or refused); the runner (a yes on the phone runs the call with nothing left waiting; no live call leaves the question in the console; "Always ask first" ignores the phone; phone tools are not served). Run live on a throwaway profile: the Phone tab, a number saved in canonical form and applied with no restart, and the status route. **Not run against the real provider**: that needs the owner's agent, number and key.

The cost of decision 7 is real and the owner takes it by switching it on. JARVIS cannot see whether the agent asked on the phone: a tool call arrives the same either way. With the setting on and the agent set to "No Approval" at ElevenLabs, the phone agent can use tools of risk 2 or less without asking anyone while a call JARVIS placed is answered, and whoever answers the owner's phone is treated as the owner. The setting says so, and the agent should be set to ask for acting tools.

Not done: calls to JARVIS recorded or recognised by JARVIS (no caller check; an inbound caller is whatever the agent makes of them, with the agent's own authentication); the post-call webhook with its signature check and a durable inbox (`P8-008`); a regional ElevenLabs host for data-residency accounts; hanging up from JARVIS; Telegram or a push when a call ends unanswered; consent and disclosure flags beyond the opening line; an opt-in live smoke test with the owner's account.
